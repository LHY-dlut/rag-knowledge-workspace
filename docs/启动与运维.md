# 启动、演示与运维

本目录是从冻结引用协议 v3 复制的独立生产候选版本。保留 FastAPI、Tortoise、MySQL、PostgreSQL + pgvector、父子分块、Vector/BM25/RRF/Rerank、显式 LangGraph、持久 SSE 和四项评测。当前验收范围与待完成门槛见 production_acceptance_plan.md。

## 首次启动

先确认 `docker info` 和 `docker compose version` 正常。需要 Python 3.12+ 生成本地配置；运行容器不需要安装宿主机 Python 依赖或 Node。所有命令在本目录执行。

```powershell
python -X utf8 scripts/setup_env.py --mode production
```

脚本生成随机数据库口令与 JWT_SECRET，不覆盖已有 `.env`、不打印秘密。先保持 `MODEL_PROVIDER=demo`，将 `ENABLE_REGISTRATION=true` 临时启用，仅在 loopback 创建自己的账号。启动固定部署规模：

```powershell
docker compose -p zhixu-rag up --build -d --scale worker=2
docker compose -p zhixu-rag ps
```

打开 http://127.0.0.1:8080。注册账号后将 `.env` 中 `ENABLE_REGISTRATION=false`，再执行 `docker compose -p zhixu-rag up -d --scale worker=2`。这会排空并更新受影响的服务；不要删除卷。Compose 项目名决定数据库卷身份，正常重启保持同一项目名。

接入百炼时填入既有凭据及对应地域的两个 API 基址，将 `MODEL_PROVIDER=dashscope`，保持模型名 qwen-plus、text-embedding-v4、gte-rerank-v2。执行上面的 up 命令更新服务，另建知识库或重建索引后验证；Demo 与真实模型向量不能混用。不要把密钥写进源码、截图或报告。

`MODEL_CONCURRENCY=1` 是每进程上限，1 API + 2 worker 最多同时发送 3 个模型请求；增加进程会改变这个上限。`MODEL_DAILY_DISPATCH_LIMIT=300` 由 MySQL 记录并跨进程串行预留，UTC 日期计数，失败、重试和断开的请求不退额。数据库预算记录不可用时不发送请求；这不是云账户金额硬限额。单次输入最多 100000 UTF-8 字节，聊天输出最多 2048 tokens；费用还需在云平台控制。

## 独立验收实例

```powershell
docker compose -p rag-prod-v14 -f compose.yml -f compose.acceptance.yml up --build -d --scale worker=2
```

本轮 v1.4 的 `.env` 使用 `RAG_HTTP_PORT=18126`。前端 18126、API 18125、MySQL 13337、PG 15463 均仅绑定 loopback；保留 v1.2/v1.3 的独立运行实例与数据。普通部署不使用这个覆盖配置。集成测试必须指向另建的空数据库并设置 `ACCEPTANCE_ISOLATED_DATABASES=1`，不能用已有业务库跑清理测试。

## 页面演示顺序

1. 创建知识库，上传 examples/差旅与休假制度.md；观察 queued/processing/ready。
2. 提问“出差报销申请需要几天内提交？”，展示最终答案、引用展开及 route 至 check 轨迹。
3. 提问资料外问题，展示拒答、检索重试次数，确认没有伪造引用。
4. 停止生成，确认取消记录终态、草稿清除；重新启动 worker 后不能发布取消请求的答案。
5. 提问后断开浏览器网络，保留后台任务；恢复网络/刷新，展示登录恢复与同一次运行的最终答案。必要时重启 API 验证持久回放。
6. 检索调试展示实际子块与父块回溯，质量评测展示逐题与缺失状态。Demo 分数不代表真实模型质量。

## 状态与排错

`/api/live` 只检查 API 进程；`/api/ready` 在有界超时内分别执行双库 SELECT 1，任一失败返回 503，不泄露连接字符串；原 `/api/health` 保留兼容用途。Compose API 健康探针使用 ready，worker 探针使用其数据库心跳文件。探针不调用模型。容器 unhealthy 需要监控告警与调查，Docker restart 策略本身不会因 unhealthy 自动重启。

```powershell
docker compose -p zhixu-rag logs --tail=80 api worker migrate
docker compose -p zhixu-rag restart api
docker compose -p zhixu-rag stop frontend api worker
```

worker 收到 SIGTERM 后停止领取，活动任务最多排空 60 秒，超过期限取消并沿用租约/发布隔离；Compose 给 75 秒退出时间。API/数据库/前端设 restart 策略，日志保留最多 3 个 10MB 文件。故障恢复记录仍须检查，重启不能证明丢失的付费请求未执行。不要强杀 Docker 后端；Desktop 故障属于宿主机环境问题。

## 双库与文件备份

备份内有用户资料，只保存到源码目录外的私有位置。先按上文排空停止 frontend/API/worker，数据库保持启动：

```powershell
python -X utf8 scripts/backup_compose.py backup --project zhixu-rag --directory D:/RAG_Backups/backup-001
docker compose -p zhixu-rag start api worker frontend
```

脚本只导出已停止写入的当前项目数据库及上传目录，保存 SHA256，不覆盖旧备份。恢复必须用全新隔离项目：先只启动其双库，并创建停止状态的 API/worker 容器；**不要执行 migrate/up 全部服务来填充目标库**。然后：

```powershell
python -X utf8 scripts/backup_compose.py restore-empty --project zhixu-rag-restore --directory D:/RAG_Backups/backup-001
```

目标数据库或上传目录非空时脚本拒绝恢复。恢复成功后还必须核对迁移、行数、向量余弦查询、上传文件哈希与实际 HTTP 答案，再启动 worker/前端。脚本会启动目标 API 并恢复 Linux 文件权限，恢复失败的目标保持为隔离故障副本，不能对它重复强制覆盖或接入业务流量。

## 使用边界

隔离实例可运行持续检查，输出目录必须在源码之外。该脚本只允许生产模式的 Demo 模型，创建独立合成账号/资料（验收时需临时开启注册），每分钟探测双库、每十分钟验证一次带引用回答，每小时重新登录。源码、配置、镜像或容器启动状态变化会记录失败并停止；不会把中断之前的时间拼成一次连续通过。

```powershell
python -X utf8 scripts/acceptance_soak.py --url http://127.0.0.1:18125 --project rag-prod-v14 --output D:/RAG_Acceptance/soak-001 --hours 24
```

`status.json` 显示 running 时仅表示正在执行；必须达到实际 24 小时且零失败才能写通过。普通 API 重启/数据库故障测试应在这段冻结观察开始前完成。Demo 观察不验证模型商的长时间可靠性。

默认是本机/小团队隔离访问。公网需 HTTPS、受控注册与访问策略、监控与备份保留策略；不要直接开放验收 API/数据库端口。当前不提供组织共享/管理员权限模型。OCR 未完成实测前不承诺扫描件支持。BM25 为进程内按版本缓存，容量上限和重建成本需按实际资料量测量。LLM 的事实核验是概率判断，引用格式与逐字证据校验不等于完整事实质量保证。
